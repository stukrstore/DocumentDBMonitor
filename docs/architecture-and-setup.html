Azure · Monitoring Guide

DocumentDB 모니터링 구조 및 설정 가이드

대상: Azure DocumentDB(MongoDB vCore) 클러스터 <doc-db-cluster-name>

목차 0. 요약 1. 전체 구조 2. Azure Monitor workspace 구성 3. 포털 없는 수집 구성 4. Grafana Dashboard 5. 메트릭 카탈로그 6. 제한 사항
이 문서의 <resource-group>, <doc-db-cluster-name> 등은 자리표시자입니다. 명령이나 설정을 실행하기 전에 각 환경의 실제 값으로 변경합니다. 리소스 그룹이 다르면 수집기, DocumentDB, Grafana 각각의 값을 사용합니다.

0. 요약

Q1. Azure Monitor workspace 구성

AMW는 Prometheus 메트릭 저장소입니다. 생성하면 DCE/DCR이 자동으로 만들어지고, 수집기(Prometheus agent)가 Managed Identity로 DCR 쓰기 URL(remote_write)에 전송합니다. Grafana는 AMW 쿼리 엔드포인트를 PromQL 데이터 소스로 읽습니다. 상세는 2장.

Q2. 별도 portal 없이 AMW에서 DocumentDB 수집 구성이 가능한가

AMW 자체에는 DocumentDB(Mongo) 수집 설정 기능이 없습니다. AMW는 수신 전용이며 DB에 접속하는 커넥터가 없습니다(Managed Prometheus의 PodMonitor/ServiceMonitor도 AKS 전용). 수집 범위에 따라 다음과 같이 나뉩니다.

  • 플랫폼 지표(CPU, 메모리, IOPS, 스토리지, 네트워크, 요청 지연): 수집기 불필요. Grafana의 Azure Monitor 데이터 소스가 직접 조회합니다. 설정 화면도 필요 없습니다.
  • DB 내부 지표(currentOp, 컬렉션/DB 크기 등): 수집기(exporter + Prometheus agent)가 필요합니다. 이때 "타겟 등록 화면"은 필수가 아닙니다. 타겟은 Key Vault 시크릿 + 태그이므로 CLI/IaC로 관리할 수 있고, UI는 선택 사항입니다(3장).

Q3. Grafana Dashboard 구성 방법

대시보드 1개(uid docdb-monitor)를 JSON으로 export 하여 전달하고, 받는 쪽은 데이터 소스 2개(Azure Monitor, AMW Prometheus)와 읽기 권한을 준비한 뒤 import 합니다. 4장 참조.

2. Azure Monitor workspace 구성

Azure CLI 아래 2-1~2-5는 Azure CLI/PowerShell 예시입니다. 2-6의 Terraform 예시는 AMW, ID 및 RBAC 범위이며 수집기를 배포하지 않습니다. 수집기는 3-4의 Azure CLI 기반 배포 스크립트로 별도 배포합니다. 두 방식이 같은 리소스를 중복 생성하지 않도록 기존 리소스 및 Terraform state를 확인하세요.

  1. AMW 생성. 기본 DCE/DCR이 함께 생성됩니다.
  2. DCR 불변 ID와 DCE 수집 엔드포인트로 remote_write URL을 구성합니다.
  3. 수집기 Managed Identity에 DCR 대상 Monitoring Metrics Publisher 역할을 부여합니다.
  4. Grafana Managed Identity에 AMW 대상 Monitoring Data Reader 역할을 부여하고, AMW 쿼리 엔드포인트를 데이터 소스로 등록합니다.

2-1. 생성과 remote_write URL

$rg = "<resource-group>"; $amwName = "<amw-name>"
az monitor account create -g $rg -n $amwName -l "<azure-region>"
$amw = az monitor account show -g $rg -n $amwName -o json | ConvertFrom-Json

$dcrId  = $amw.defaultIngestionSettings.dataCollectionRuleResourceId
$dceId  = $amw.defaultIngestionSettings.dataCollectionEndpointResourceId
$dcrImm = az rest --method get --url "https://management.azure.com$($dcrId)?api-version=2022-06-01" --query properties.immutableId -o tsv
$dceUrl = az rest --method get --url "https://management.azure.com$($dceId)?api-version=2022-06-01" --query properties.metricsIngestion.endpoint -o tsv

# Prometheus remote_write url
"$dceUrl/dataCollectionRules/$dcrImm/streams/Microsoft-PrometheusMetrics/api/v1/write?api-version=2023-04-24"

# 쿼리 엔드포인트 (Grafana 데이터 소스용)
$amw.metrics.prometheusQueryEndpoint

2-2. 수집기 쓰기 권한

az role assignment create --assignee-object-id "<collector-managed-identity-principal-id>" `
  --assignee-principal-type ServicePrincipal `
  --role "Monitoring Metrics Publisher" --scope $dcrId

2-3. Prometheus agent 설정 (remote_write 부분)

remote_write:
  - url: "<remote-write-url>"
    azuread:
      cloud: AzurePublic
      managed_identity:
        client_id: "<collector-managed-identity-client-id>"
    write_relabel_configs:
      - source_labels: [__name__]
        regex: "docdb_.*|up"
        action: keep

2-4. Grafana 읽기 권한과 데이터 소스

# AMW PromQL 조회
az role assignment create --assignee-object-id "<grafana-managed-identity-principal-id>" `
  --assignee-principal-type ServicePrincipal `
  --role "Monitoring Data Reader" --scope $amw.id

# Azure Monitor 플랫폼 지표 조회 (대상 클러스터 리소스 그룹)
az role assignment create --assignee-object-id "<grafana-managed-identity-principal-id>" `
  --assignee-principal-type ServicePrincipal `
  --role "Monitoring Reader" --scope "/subscriptions/<subscription-id>/resourceGroups/<doc-db-resource-group>"

데이터 소스 정의(Prometheus): type grafana-azureprometheus-datasource, url = AMW 쿼리 엔드포인트, 인증 Managed Identity(azureCredentials.authType = msi), uid docdb-amw. 자동화 스크립트는 grafana/deploy-grafana.ps1입니다.

2-5. 확인

$t = az account get-access-token --resource https://prometheus.monitor.azure.com --query accessToken -o tsv
Invoke-RestMethod -Headers @{Authorization="Bearer $t"} `
  -Uri "$($amw.metrics.prometheusQueryEndpoint)/api/v1/query?query=docdb_up"
AMW 요금은 수집 샘플 수에 비례합니다. 샘플 수 = (대상 수) × (수집 주기당 시리즈 수) 이므로, 테스트 후에는 수집 주기를 5s에서 1m으로 되돌리는 것을 권장합니다.

2-6. Terraform 버전

Terraform AMW, 수집기 Managed Identity, AMW 쓰기 권한과 Grafana 읽기 권한을 선언합니다. 예시는 AzureRM 5.x 기준이며 main.tf, main.tfvars.json, outputs.tf로 분리합니다. 기존 Grafana와 클러스터 리소스 그룹은 변수로 전달합니다.

main.tf

terraform {
  required_version = ">= 1.8.0"
  required_providers {
    azurerm  = { source = "hashicorp/azurerm", version = "~> 5.0" }
    azurecaf = { source = "aztfmod/azurecaf", version = "~> 1.2" }
  }
}

provider "azurerm" {
  subscription_id = var.subscription_id
  features {}
}

variable "subscription_id" {}
variable "location"          { type = string }
variable "resource_group"    { type = string }
variable "amw_name_base"     { type = string }
variable "collector_identity_name" { type = string }
variable "grafana_principal_id" { description = "Managed Grafana의 principalId" }
variable "cluster_resource_group_id" {
  description = "DocumentDB 리소스 그룹의 전체 resource ID"
}

resource "azurecaf_name" "amw" {
  name          = var.amw_name_base
  resource_type = "azurerm_monitor_workspace"
  clean_input   = true
}

resource "azurerm_resource_group" "monitor" {
  name     = var.resource_group
  location = var.location
}

resource "azurerm_user_assigned_identity" "collector" {
  name                = var.collector_identity_name
  resource_group_name = azurerm_resource_group.monitor.name
  location            = azurerm_resource_group.monitor.location
}

resource "azurerm_monitor_workspace" "docdb" {
  name                          = azurecaf_name.amw.result
  resource_group_name           = azurerm_resource_group.monitor.name
  location                      = azurerm_resource_group.monitor.location
  public_network_access_enabled = true
}

# 이름 대신 role_definition_name을 사용하여 Cloud별 역할 GUID 차이를 피한다.
resource "azurerm_role_assignment" "collector_publish" {
  scope                = azurerm_monitor_workspace.docdb.default_data_collection_rule_id
  role_definition_name = "Monitoring Metrics Publisher"
  principal_id         = azurerm_user_assigned_identity.collector.principal_id
  principal_type       = "ServicePrincipal"
}

resource "azurerm_role_assignment" "grafana_amw_read" {
  scope                = azurerm_monitor_workspace.docdb.id
  role_definition_name = "Monitoring Data Reader"
  principal_id         = var.grafana_principal_id
  principal_type       = "ServicePrincipal"
}

resource "azurerm_role_assignment" "grafana_platform_read" {
  scope                = var.cluster_resource_group_id
  role_definition_name = "Monitoring Reader"
  principal_id         = var.grafana_principal_id
  principal_type       = "ServicePrincipal"
}

Terraform의 azurerm_monitor_workspace는 기본 DCR/DCE ID와 Prometheus 쿼리 엔드포인트를 출력하지만, DCR immutable ID와 DCE의 metrics ingestion endpoint를 직접 출력하지는 않습니다. 따라서 Prometheus remote_write URL은 배포 후 2-1의 Azure CLI 조회로 생성하거나 별도 azapi 데이터 조회를 추가합니다. 현재 배포 스크립트도 이 방식입니다.
이 Terraform 예제는 새 AMW와 Managed Identity를 생성합니다. 기존 리소스에 적용하려면 기존 이름과 ID를 확인하고 Terraform state로 import한 후 plan을 검토하세요. <amw-name-base>는 CAF 이름 생성 입력이므로 실제 생성된 AMW 이름을 output 또는 state에서 확인해 CLI 단계의 <amw-name>에 사용합니다.

3. 포털 없는 수집 구성

3-1. 어디까지 AMW만으로 되는가

대상AMW 단독필요한 것
플랫폼 지표(CPU/Mem/IOPS/Storage/Network/요청 지연)수집기 불필요Grafana Azure Monitor 데이터 소스 + Monitoring Reader. 설정 UI 없음
DB 내부 지표(currentOp, 컬렉션/DB 크기)불가DB에 접속하는 exporter와 Prometheus agent. AMW는 수신 전용
AKS의 Managed Prometheus PodMonitor/ServiceMonitor해당 없음AKS 클러스터 전용 기능이며 DocumentDB 수집에는 사용할 수 없음

3-2. 복잡도를 줄이는 방법

수집 설정 UI가 부담스러우면 아래 순서로 단순화할 수 있습니다.

  1. 플랫폼 지표만 사용: 수집기·Key Vault·ACA를 모두 제거합니다. 대시보드의 Azure Monitor 섹션과 ServerName 분할 패널만으로 노드별 부하 불균형을 볼 수 있습니다. DB 내부 지표(currentOp, 컬렉션 크기)는 포기합니다.
  2. UI 없이 CLI/IaC로 타겟 관리: 수집기는 Key Vault 시크릿을 읽으므로, 타겟 추가는 시크릿 생성만으로 됩니다(아래). UI는 두지 않아도 동작합니다.
  3. 고정 설정: Prometheus static_configs와 환경 변수로 타겟을 1개 고정하고 IaC(Bicep)로 배포합니다. 변경은 재배포로만 가능합니다.

3-3. CLI로 타겟 추가/변경 (UI 없이)

수집기는 접두사 docdb-, 태그 app=docdb-monitor인 시크릿을 타겟으로 인식하고, 약 30초마다 목록을 갱신합니다.

$kv = "<key-vault-name>"
$targetName = "<doc-db-cluster-name>"
$hostName = "<doc-db-hostname>"
az keyvault secret set --vault-name $kv --name "docdb-$targetName" `
  --value "<documentdb-connection-string>" `
  --tags app=docdb-monitor "host=$hostName" interval=1m enabled=true collstats=true note=

# 설정만 변경 (접속 문자열 유지): 수집 주기 1m, collStats 끄기
az keyvault secret set-attributes --vault-name $kv --name "docdb-$targetName" `
  --tags app=docdb-monitor "host=$hostName" interval=1m enabled=true collstats=false note=
접속 문자열을 명령줄에 직접 입력하면 셸 기록이나 프로세스 정보에 노출될 수 있습니다. 안전한 비밀 주입 방식을 사용하고 명령 출력도 보호하세요. 시크릿 태그 수정 시 필요한 태그를 모두 다시 지정해야 합니다.
태그값의미
interval5s, 10s, 15s, 30s, 1m, 2m, 5m수집 주기. 5m 초과는 Prometheus 5분 조회 구간 때문에 시리즈가 끊김
enabledtrue / false수집 on/off
collstatstrue / false컬렉션/DB 크기 수집(10분 주기 캐시). 컬렉션이 많으면 false 권장
Key Vault가 Private Endpoint 전용이라면 로컬 PC에서 az keyvault secret set이 실패할 수 있습니다. 정책에 맞는 네트워크 및 DNS 경로가 있는 환경에서 실행하세요. UI를 통하거나 VNet 내부 실행 환경을 사용할 수 있습니다.

3-4. 수집기 배포 (한 번만)

.\deploy.ps1 -ResourceGroup "<resource-group>" -Location "<azure-region>" `
  -VnetResourceGroup "<vnet-resource-group>" -VnetName "<vnet-name>" -EnvName "<container-app-environment-name>"

스크립트는 기본 prefix와 구독/리소스 그룹에서 일부 리소스 이름을 생성합니다. 생성된 실제 이름을 확인하고 각 자리표시자에 사용하세요. 기존 VNet을 사용할 때는 겹치지 않는 -AcaSubnetPrefix와 실제 Private Endpoint 서브넷을 지정하세요.

생성되는 것: ACR, Managed Identity, Key Vault(+Private Endpoint), AMW, ACA 환경/앱(app + prometheus), 역할 할당(AcrPull, Monitoring Metrics Publisher, Key Vault Secrets Officer, 커스텀 Discovery), Entra 앱 등록(Easy Auth). 재실행 가능합니다.

배포 중 외부 ingress가 인증 설정보다 먼저 생성됩니다. 인증 설정 실패 시 직접 요청이 유입되지 않도록 배포 전 네트워크 접근을 제한하고 Easy Auth 및 접근 제한을 검증하세요. 스크립트는 인증 비밀을 Azure CLI 명령줄에 전달하므로 신뢰된 실행 환경이 필요합니다.

3-5. 네트워크 전제

  • ACA 환경이 DocumentDB Private Endpoint가 있는 VNet에 통합되어야 합니다.
  • privatelink.mongocluster.cosmos.azure.com 프라이빗 DNS 존이 해당 VNet에 링크되어 있어야 합니다.
  • privatelink.vaultcore.azure.net 존도 같은 VNet에 링크되어야 Key Vault를 읽을 수 있습니다.

3-6. Terraform으로 수집 대상 관리 (UI 없음)

기존 Private Key Vault를 Terraform data source로 읽고 azurerm_key_vault_secret을 선언하면 UI 없이 같은 타겟 설정을 관리할 수 있습니다. 접속 문자열은 코드에 넣지 않고 TF_VAR_documentdb_uri 환경 변수 또는 비밀 변수 저장소에서 주입합니다.

variable "key_vault_name"       { type = string }
variable "key_vault_rg"         { type = string }
variable "doc_db_cluster_name"  { type = string }
variable "documentdb_uri"       { sensitive = true }
variable "documentdb_host"      {}
variable "collection_interval"  { default = "1m" }
variable "collection_enabled"   { default = true }
variable "collection_collstats" { default = true }

data "azurerm_key_vault" "monitor" {
  name                = var.key_vault_name

6. 제한 사항

  • serverStatus 미지원: DocumentDB vCore는 serverStatus를 지원하지 않아(CommandNotSupported) opcounters, 연결 수, 캐시 지표 등은 수집할 수 없습니다. 요청/지연은 Azure Monitor MongoRequestDurationMs로 대체합니다.
  • 샤드별 데이터 통계 미지원: $shardedDataDistribution, $collStats, collStats 명령 모두 컬렉션 합계만 반환합니다(확인함). 샤드 쏠림은 Azure Monitor의 ServerName별 요청·지연·네트워크 차이로 간접 판단합니다. 데이터량 쏠림은 직접 측정할 수 없습니다.
  • 수집 주기 상한 5m: 5분 초과 시 Prometheus staleness로 시리즈가 끊깁니다.
  • collStats 비용: 컬렉션 수에 비례해 부하가 늘어납니다. 상한 100개(COLLSTATS_MAX_COLLECTIONS), 10분 주기 캐시(COLLSTATS_INTERVAL_SECS).
  • 보안: 운영 연결 문자열은 Key Vault에 저장하고 UI/API는 반환하지 않습니다. 로컬 개발 저장소는 평문이므로 실제 비밀을 넣지 마세요.
